# Лабораторная работа 4 — динамические свойства сущностей

## 1. Где в библиотеках встречается контекст с динамическими свойствами

Я нашёл такой контекст в библиотеках и фреймворках, которые сами не знают,
какие данные туда положит пользователь. Библиотека определяет только контейнер
и правила доступа, а конкретные ключи и типы придумывает потребитель:

- **ASP.NET Core, `HttpContext.Items`**: middleware может записать
  `context.Items["correlation-id"] = correlationId`, а другой middleware или
  контроллер прочитать его по тому же ключу. Сам ASP.NET Core не знает, что
  такое `correlation-id`.
- **ASP.NET Core, `AuthenticationProperties.Items`**: схема аутентификации
  сохраняет произвольные данные (`redirect_uri`, `tenant`, токены), которые
  нужны только конкретному handler'у.
- **MVC, `ActionExecutingContext.ActionParameters` / `HttpContext.Items`**:
  фильтры обмениваются данными с действиями через словарь, не добавляя поля в
  сам `ActionExecutingContext`.
- **FluentValidation, `ValidationContext.RootContextData`**: вызывающий код
  кладёт туда, например, текущего пользователя или ID организации, а валидатор
  читает это, хотя библиотека валидации ничего об этих типах не знает.
- **HotChocolate, `IResolverContext.ContextData`**: резолверы графа передают
  друг другу данные запроса через общий словарь.
- **WPF, attached behaviors/свойства**: поведение приклеивается к готовому
  контролу извне, без изменения класса контрола.

Общий смысл: **библиотека даёт контейнер, а пользователь — схему данных**.
Именно такую схему я и воспроизвёл в лабораторной: моя библиотека `context`
ничего не знает про `Health` или `Team`, но позволяет другим проектам договариваться
об их ключах.

## 2. Почему `FatStruct` не подходит, если его определяет библиотека

`FatStruct` — это одна структура, в которую заранее включены все возможные
поля:

```java
public final class Entity {
    public String name;
    public Health health;
    public Position position;
    public Poison poison;
    public Team team;   // <- пришлось бы добавить в библиотеку
}
```

Я пришёл к выводу, что в библиотеке это не работает по четырём причинам:

1. **Библиотека не знает своих пользователей.** Чтобы добавить поле `Team`,
   она должна либо импортировать тип из проекта потребителя (циклическая
   зависимость), либо заставить всех пользователей согласиться с её набором полей.
2. **Нарушается open/closed principle.** Появление нового компонента требует
   изменения и перекомпиляции самой библиотеки, а не только одного модуля.
3. **Память и проверки.** Каждая сущность платит за все поля, даже если они
   не используются; перед чтением надо проверять «а заполнено ли поле?», то есть
   всё равно получается динамическая структура, только неэффективная.
4. **Нет независимого версионирования.** Два потребителя не могут по-разному
   расширять одну и ту же сущность: они обязаны синхронно обновлять библиотеку.

Поэтому для библиотеки нужен контейнер, который **не фиксирует схему на этапе
компиляции библиотеки**.

## 3. Как я добился того, что один проект работает с сущностями другого

Я сделал три модуля:

| Модуль | Роль |
| --- | --- |
| `context` | библиотека: `Entity`, `PropertyKey<T>`, `KeyRegistry`, `Operation`, `Operations`, `OperationPipeline` |
| `entities` | отдельный проект: части сущности `Name`, `Health`, `Position`, `Poison` и операции `HealOperation`, `MoveOperation`, `PoisonOperation` |
| `app` | потребитель: свои части `Team`, `Buff`, свои операции `BuffOperation`, `TeamReportOperation` и точка входа `App` |

Внутри `Entity` лежит ассоциативный массив `Map<Integer, Object>`: ключом служит
целый `id`, выданный реестром. Пользователь видит только типизированную обёртку
`PropertyKey<T>`, поэтому `set`/`get` проверяются компилятором:

```java
Entity hero = new Entity()
    .set(Name.KEY, Name.of("Герой"))       // компонент из entities
    .set(Health.KEY, Health.of(80, 100))   // компонент из entities
    .set(Team.KEY, Team.of("союзники"));   // компонент из app

OperationPipeline pipeline = new OperationPipeline()
    .add(new HealOperation(15))      // операция из entities
    .add(new BuffOperation())        // операция из app
    .add(new PoisonOperation())      // операция из entities
    .add(new MoveOperation(2, -1))   // операция из entities
    .add(new TeamReportOperation()); // операция из app

pipeline.run(hero);
```

Библиотека `context` не импортирует `entities` и `app`: она умеет только
прогонять `Operation` по `Entity`. Сами операции решают, применимы ли они:
`HealOperation` проверяет `entity.has(Health.KEY)`, `BuffOperation` требует
одновременно `Health.KEY` из чужого проекта и `Buff.KEY` из своего, а
`PoisonOperation` после двух ходов **удаляет** компонент `Poison` через
`entity.remove(Poison.KEY)`. То есть набор частей сущности меняется во время
выполнения программы. Для простых случаев я также добавил helper
`Operations.when(body, keys...)`, который создаёт операцию, выполняемую только
при наличии перечисленных ключей.

## 4. Централизованный реестр ключей

Чтобы два проекта не записали разные данные под одним и тем же ключом, я
использовал оба описанных в задании приёма сразу:

- ключ — обёртка над `int id` (`PropertyKey<T>`);
- ключи регистрируются в глобальном `KeyRegistry`, и повторная регистрация
  того же имени — ошибка.

```java
public static final PropertyKey<Health> KEY =
    KeyRegistry.register("lab4.entities.health", Health.class);

public static final PropertyKey<Team> KEY =
    KeyRegistry.register("lab4.app.team", Team.class);

// KeyRegistry.register("lab4.entities.health", Team.class) ->
// IllegalArgumentException: Ключ уже зарегистрирован...
```

`KeyRegistry` хранит `имя -> ключ` и `id -> ключ`, выдаёт уникальные `id` и
методом `lookup(name, Class<T>)` возвращает тот же типизированный ключ с
проверкой типа. Дополнительно `Entity.set` проверяет
`key.type().isInstance(value)`, поэтому даже через приведённый вручную
"фальшивый" `PropertyKey<Integer>` нельзя записать число в ключ `String`.
В тесте это специально проверяется. Благодаря этому `entities` и `app` могут
работать с одной и той же сущностью, но не могут случайно переопределить
чужой ключ.

## 5. Что я изучил и как мыслил при выборе подхода

Я рассмотрел подходы по порядку из задания:

1. **Иерархии классов.** Свойства задаются статически через наследование;
   интерфейсы обходят отсутствие множественного наследования, а паттерн
   traits позволяет не дублировать хранение. Минус для моей задачи: структура
   фиксируется на этапе компиляции, комбинации свойств требуют новых классов,
   во время выполнения конфигурировать их нельзя.
2. **`object[]`.** Очень простой массив, для примитивов нужны теги. Но два
   проекта должны договориться о номерах ячеек; легко перепутать индексы,
   нет проверки типов, при удалении компонента остаются "дыры". Поэтому я
   выбрал словарь, а не массив.
3. **`FatStruct`.** Проще всего читать, но, как я написал выше, неприменим в
   библиотеке: тратит память, требует проверок на наличие и зависит от кода
   пользователей.
4. **Ассоциативный массив.** Даёт нужную динамику: ключ можно создать в любом
   модуле. Минус классической версии — каст при чтении и отдельный объект на каждое
   свойство. Я устранил каст с помощью generic-обёртки `PropertyKey<T>`, а
   конфликты имен — реестром.
5. **ECS (sparse set / архетипы, EnTT, Unity DOTS).** Самый производительный
   вариант для тысяч сущностей, но для этого задания он избыточен: здесь
   важно показать изоляцию библиотеки и защиту ключей, а не массовую
   обработку. Я оставил его как следующий шаг.

Итог: я выбрал **словарь + типизированный ключ + центральный реестр**. Это
минимальный набор, который одновременно закрывает пункты 3 и 4 задания и
остаётся понятным.

## Как запускать

Нужны JDK 21 (Gradle сам подтянет toolchain, если его нет) и Gradle Wrapper
(он уже лежит в репозитории). Из корня проекта:

```bash
./gradlew run     # или: just run  — запуск демонстрации
./gradlew test    # или: just test — прогон тестов
./gradlew build   # или: just build — полная сборка
```

Точка входа: `org.example.app.App` (модуль `app`).

Пример вывода `./gradlew run --quiet`:

```text
=== Ход 1 ===
  [entities] Герой: лечение +15 -> 95/100
  [app] Герой: бафф +10 использован -> 100/100
  [entities] Герой: яд 5 -> 95/100
  [entities] Герой: перемещение -> (2, -1)
  [app] союзники | Герой | HP 95/100 | позиция (2, -1)
  [entities] Сундук: перемещение -> (5, 3)
  [app] нейтральные | Сундук | HP — | позиция (5, 3)
  ...
=== Итоговые состояния ===
Entity#1{lab4.entities.name=Герой, lab4.entities.health=95/100, lab4.entities.position=(4, -2), lab4.app.team=союзники}
...
```

Видно, что `Сундук` не лечится и не отравляется (у него нет `Health`), но
перемещается (есть `Position`), а `Герой` теряет `Buff` и `Poison` по ходу
программы — именно это и есть динамические свойства.

## Тесты

- `context/.../KeyRegistryTest` — уникальность и проверка типов ключей,
  ошибка при повторной регистрации.
- `context/.../EntityTest` — чтение/запись/удаление по типизированному ключу,
  защита от подмены типа и условная операция `Operations.when`.
- `app/.../IntegrationTest` — `app` обрабатывает сущности из `entities`,
  операции пропускаются без нужных компонентов, `Poison` удаляется, реестр
  не даёт двум модулям зарегистрировать один ключ.

Все тесты проходят: `./gradlew build` завершается `BUILD SUCCESSFUL`.
